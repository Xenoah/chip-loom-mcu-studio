# v0.1.0-pre.0 — Phase 0: Foundation

**This is a prerelease.** It is development history, published so the construction
of Chip Loom can be followed and evaluated. It is not a finished product, and it is
not intended for production use. `v1.0.0` will be the first finished release.

**What this version does not do:** it does not build firmware, does not flash a
device, does not monitor a serial port and does not debug anything. Those are
Phases 3, 4, 5 and 6. This release delivers the foundation they are built on.

## English

### What this phase added

Phase 0 establishes the structure the rest of Chip Loom is built on, and the rules
that keep it honest.

**One core, two front ends.** `chiploom-core` makes every decision and holds no
terminal: it never prints and never exits. The `chiploom` CLI renders those
decisions for a person and picks the process exit code. The VS Code extension
renders the same values in an editor, over a documented protocol, with no
privileged path into the core. The result is that nothing the editor can do is
unavailable from the command line.

**Layered configuration that behaves correctly.** Defaults, then the user-global
`config.toml`, then the project's `chiploom.toml`, then `CHIPLOOM_*` environment
variables, then command-line flags. Layers are merged as optional patches, so a
project file that says nothing about `log.level` leaves the global value alone
instead of overwriting it with the default. Unknown keys are collected rather than
rejected, so a project pinned to an older Chip Loom can still read a file written
by a newer one. Every consulted layer is reported — including the ones that were
missing — which is what lets `chiploom config show --sources` answer *why* a value
is what it is.

**Diagnostics worth running.** `chiploom doctor` runs eleven checks covering this
binary, the host, the configuration, all three storage directories, the project,
`git`, the VS Code CLI and, on request, network reachability. A directory check
creates the directory, writes a probe file, reads it back and deletes it — a bare
existence test passes on read-only mounts and on Windows directories that deny
writes, which is exactly the case worth catching. Anything actionable carries a
hint. A check never aborts the run: a diagnostic tool that stops halfway is useless
on the one machine that needs it.

**A protocol, specified and tested.** JSON-RPC 2.0 over newline-delimited stdio,
protocol version 1, with version negotiation that refuses a mismatch rather than
guessing, and capability-based feature discovery so clients branch on the method
list instead of a version string. stdout carries only protocol frames; every
diagnostic goes to stderr. There is a test that runs the server at `-vvv` and
parses every stdout line as JSON, so logging cannot corrupt a session.

**Errors that can be acted on.** One error type, a variant per failure class, each
mapped to a documented and test-asserted exit code. Failures name their subject —
the path and the operation, not just "permission denied" — and carry remediation
text where one applies. `Error::kind` is a stable string, so JSON output and
JSON-RPC errors can be branched on without parsing prose.

**Cross-platform CI, and a release pipeline that refuses to ship a broken
artifact.** CI runs formatting, clippy with warnings denied, the full test suite,
the extension type-check and the extension's protocol tests on Windows, macOS and
Linux, and then runs the three Phase 0 acceptance commands directly. The release
workflow builds five target triples, runs `--version` and `doctor` on each native
binary before packaging it, and writes a SHA-256 next to every archive.

#### Commands

| Command | What it does |
| --- | --- |
| `chiploom --version` | The version, and the commit it was built from. |
| `chiploom --help` | Every command and option. |
| `chiploom doctor` | Checks whether this machine can run Chip Loom, and says what to fix. |
| `chiploom version -v` | Full build provenance, for bug reports. |
| `chiploom config show` | The effective configuration, as pasteable TOML. |
| `chiploom config path` | Every location configuration and data is read from. |
| `chiploom config check` | Validates configuration files and reports ignored keys. |
| `chiploom serve --stdio` | Runs the Core IPC server that editors talk to. |
| `chiploom completions <shell>` | Completion script for bash, zsh, fish, PowerShell or Elvish. |

#### VS Code extension

Commands: **Show Core Version**, **Run Diagnostics**, **Restart Core**,
**Show Output**. A status bar item reports the connected core's version; an output
channel carries the core's stderr verbatim. Settings: `chiploom.corePath`,
`chiploom.autoStart`, `chiploom.logLevel`, `chiploom.startupTimeoutMs`.

The extension prefers a binary from `chiploom.corePath`, then `CHIPLOOM_BIN`, then
the workspace `target/release` and `target/debug`, then `PATH` — so a contributor
always runs the core they just built. When none is found, the error lists every
place it looked.

### Supported MCUs and boards

**None yet.** MCU and board support begins in Phase 1 (`v0.2.0-pre.0`), which adds
the MCU database, target packs and board profiles. This release has no target
database and no notion of a specific chip.

This is stated explicitly rather than omitted: nothing in this release should be
read as claiming support for any device.

### Supported operating systems

| Platform | Test suite run | Release artifact executed |
| --- | --- | --- |
| Linux x86-64 (`x86_64-unknown-linux-gnu`) | **Yes** — by hand and in CI | **Yes** — by hand and in the release workflow |
| Windows x86-64 (`x86_64-pc-windows-msvc`) | **Yes** — in CI | Yes — `--version`, `--help` and `doctor` in the release workflow |
| macOS Apple Silicon (`aarch64-apple-darwin`) | **Yes** — in CI | Yes — `--version`, `--help` and `doctor` in the release workflow |
| macOS Intel (`x86_64-apple-darwin`) | No | **No** — cross-compiled; the macOS runner is Apple Silicon with no Rosetta |
| Linux ARM64 (`aarch64-unknown-linux-gnu`) | No | **No** — cross-compiled on an x86-64 runner |

The full test suite — Rust and extension — runs on Windows, macOS and Linux in CI,
and the three acceptance commands are run directly on each. The release workflow
additionally runs `--version`, `--help` and `doctor` on each artifact it can
execute, and refuses to publish one that fails.

Two artifacts are cross-compiled and therefore **were never executed**: the Intel
macOS build (the macOS runner is Apple Silicon and has no Rosetta) and the ARM64
Linux build (cross-compiled on an x86-64 runner). They compile and link, and
nothing more than that is claimed for them. Treat them as untested until a later
prerelease says otherwise.

The code is written to be portable — no `unsafe`, platform locations through the
`directories` crate, no shelling out to platform tools — and the Windows CI run is
what caught the one portability bug found during this phase: redirecting `%APPDATA%`
does not move Chip Loom's storage, because the platform locations come from the
Known Folder API. That is why `CHIPLOOM_CONFIG_DIR`, `CHIPLOOM_DATA_DIR` and
`CHIPLOOM_CACHE_DIR` exist, and why the integration tests isolate themselves with
those rather than with `HOME`.

### Supported toolchains

**None yet.** Toolchain management is Phase 2 (`v0.3.0-pre.0`), which adds
automatic download, SHA-256 verification, extraction, caching and version pinning
for ARM GCC, AVR GCC, RISC-V GCC, Xtensa GCC and LLVM/Clang. This release does not
download, install or invoke any compiler.

To build Chip Loom itself you need Rust stable 1.88 or newer, and Node.js 20 or
newer for the extension.

### Known issues

1. **Two artifacts were never executed.** `x86_64-apple-darwin` and
   `aarch64-unknown-linux-gnu` are cross-compiled, so the release workflow could not
   run them. They compile and link; nothing more is claimed. The other three are
   executed in CI and in the release workflow, and Linux x86-64 was additionally
   verified by hand.
2. **The extension was not loaded in a live VS Code window for this release.** Its
   protocol layer — binary discovery, handshake, every method, error handling,
   shutdown — is verified by automated tests against the real binary, and that is
   what the transcript above shows. Activation inside an Extension Development Host,
   and the status bar and output channel as rendered by VS Code, were not exercised
   in the environment this release was built in. They are covered by the Phase 10
   verification plan, and earlier if a prerelease makes it practical.
3. **The `.vsix` is not published to the Marketplace.** The extension is not yet
   listed; install it from the attached `.vsix` with
   `code --install-extension chiploom-v0.1.0-pre.0.vsix`, or run it from source.
4. **The IPC server is single-threaded and synchronous.** One request is handled at
   a time, and there is no cancellation. That is sufficient for the methods in this
   release, all of which return in milliseconds. Streaming and cancellation arrive
   with the build engine in Phase 3 and the monitor in Phase 5.
5. **`doctor --online` tests TCP reachability only.** It confirms a connection can be
   opened to `github.com:443` and `crates.io:443`; it does not test an HTTP proxy,
   TLS interception or authentication. Full download verification arrives with the
   toolchain manager in Phase 2.
6. **No `aarch64-apple-darwin` code signing or notarisation.** The macOS artifacts
   are unsigned, so Gatekeeper will quarantine them. Remove the attribute with
   `xattr -d com.apple.quarantine ./chiploom` after unpacking.
7. **`commit` reads `unknown` in a build from a source archive.** The value comes from
   `git` at build time; a tarball without `.git` has nothing to read. The release
   workflow checks out full history so published binaries carry it.

## 日本語

### このフェーズで追加した機能

Phase 0 は、以降のすべてのフェーズが載る構造と、それを守るための規則を確立します。

**1つの Core と 2つのフロントエンド。** `chiploom-core` がすべての判断を行い、端末を
持ちません。出力も終了もしません。`chiploom` CLI はその判断を人向けに整形し、プロセスの
終了コードを決めます。VS Code Extension は同じ値をエディタ上に表示しますが、Core への
特権的な経路は持たず、文書化されたプロトコルだけを使います。結果として「エディタからは
できるが CLI からはできない操作」が存在しません。

**正しく動作する階層的設定。** 既定値 → ユーザ全体の `config.toml` → プロジェクトの
`chiploom.toml` → `CHIPLOOM_*` 環境変数 → コマンドライン引数の順に重ねます。各層は
「すべての項目が省略可能なパッチ」として合成されるため、`log.level` に言及しない
プロジェクトファイルが、上位層の値を既定値で上書きしてしまうことはありません。
未知のキーは拒否せず収集するため、古い Chip Loom に固定したプロジェクトでも、新しい
Chip Loom が書いた設定ファイルを読めます。参照した層は「存在しなかった層も含めて」
すべて記録されます。これにより `chiploom config show --sources` が、値そのものではなく
「なぜその値になったのか」に答えられます。

**実際に役に立つ診断。** `chiploom doctor` は、このバイナリ、ホスト環境、設定、
3つの保存領域、プロジェクト、`git`、VS Code CLI、そして要求時のみネットワーク到達性を
検査します（計11項目）。ディレクトリ検査は、作成し、プローブファイルを書き、読み戻し、
削除します。単なる存在確認は読み取り専用マウントや書き込みを拒否する Windows の
ディレクトリでも成功してしまうため、まさにそこを捕まえるためです。対処が必要な項目には
必ず対処方法を添えます。また、検査は途中で中断しません。途中で止まる診断ツールは、
それを最も必要とする環境で役に立ちません。

**仕様化され、テストされたプロトコル。** 改行区切り JSON over stdio 上の JSON-RPC 2.0、
プロトコル version 1。バージョン不一致は推測せず拒否します。機能検出は capability
方式なので、クライアントはバージョン文字列ではなくメソッド一覧で分岐します。stdout は
プロトコル専用で、診断出力はすべて stderr へ送られます。`-vvv` でサーバを動かし、
stdout の全行が JSON として解釈できることを検証するテストがあるため、ログがセッションを
壊すことはありません。

**対処可能なエラー。** エラー型は1つ、失敗の種類ごとにバリアントを持ち、それぞれが
文書化され、テストで値を固定した終了コードに対応します。失敗は対象を明示します
（「permission denied」だけでなく、パスと操作内容）。対処方法がある場合は必ず添えます。
`Error::kind` は安定した文字列なので、JSON 出力や JSON-RPC エラーを文面の解析なしに
分岐できます。

**クロスプラットフォーム CI と、壊れた成果物を公開しないリリース経路。** CI は
Windows／macOS／Linux で、フォーマット検査、警告をエラー扱いにした clippy、全テスト、
Extension の型検査とプロトコルテストを実行し、さらに Phase 0 の受け入れコマンド3種を
直接実行します。リリースワークフローは5つのターゲットトリプルをビルドし、各ネイティブ
バイナリで `--version` と `doctor` を実行してから梱包し、すべてのアーカイブに
SHA-256 を添付します。

| `chiploom --version` | バージョンと、ビルド元のコミット。 |
| `chiploom --help` | 全コマンドとオプション。 |
| `chiploom doctor` | この環境で動作するかを検査し、対処方法を示します。 |
| `chiploom version -v` | Build 情報の全項目。不具合報告に添付してください。 |
| `chiploom config show` | 有効な設定を、貼り付け可能な TOML として出力。 |

| `chiploom serve --stdio` | エディタが接続する Core IPC サーバを起動。 |
| `chiploom completions <shell>` | bash／zsh／fish／PowerShell／Elvish 用補完スクリプト。 |

#### VS Code Extension

コマンドは **Show Core Version**／**Run Diagnostics**／**Restart Core**／
**Show Output** の4つ。ステータスバーに接続中の Core のバージョンを表示し、
Output チャネルに Core の stderr をそのまま流します。設定項目は
`chiploom.corePath`／`chiploom.autoStart`／`chiploom.logLevel`／
`chiploom.startupTimeoutMs`。

バイナリの探索順は `chiploom.corePath` → `CHIPLOOM_BIN` → Workspace の
`target/release`・`target/debug` → `PATH` です。開発者が常に「たった今ビルドした Core」
を動かせるようにするためです。見つからない場合は、探索したすべての場所を列挙します。

### 対応MCU／Board

**まだありません。** MCU と Board の対応は Phase 1（`v0.2.0-pre.0`）から始まります。
MCU Database、Target Pack、Board Profile はそのフェーズで追加します。本リリースには

### 対応OS

| プラットフォーム | テスト実行 | 成果物の実行 |
| --- | --- | --- |
| Linux x86-64 (`x86_64-unknown-linux-gnu`) | **済** — 手動および CI | **済** — 手動およびリリースワークフロー |
| Windows x86-64 (`x86_64-pc-windows-msvc`) | **済** — CI | 済 — ワークフロー上で `--version`／`--help`／`doctor` |
| macOS Apple Silicon (`aarch64-apple-darwin`) | **済** — CI | 済 — ワークフロー上で `--version`／`--help`／`doctor` |
| macOS Intel (`x86_64-apple-darwin`) | 未実施 | **未実施** — クロスコンパイル。macOS ランナーは Apple Silicon で Rosetta なし |
| Linux ARM64 (`aarch64-unknown-linux-gnu`) | 未実施 | **未実施** — x86-64 ランナー上でのクロスコンパイル |

Rust と Extension の全テストは CI 上で Windows／macOS／Linux で実行し、受け入れ
コマンド3種も各 OS で直接実行しています。リリースワークフローは、実行可能な成果物に
対して `--version`／`--help`／`doctor` を実行し、失敗した成果物は公開しません。

2つの成果物はクロスコンパイルのため **一度も実行していません**。macOS Intel 版
（macOS ランナーは Apple Silicon で Rosetta 未搭載）と Linux ARM64 版
（x86-64 ランナー上でのクロスコンパイル）です。コンパイルとリンクが通ること以上は
主張していません。後続の Prerelease で明示されるまで未検証として扱ってください。

コードは移植性を意識して書かれています（`unsafe` なし、プラットフォーム固有パスは
`directories` クレート経由、OS コマンドの呼び出しなし）。本フェーズで見つかった唯一の
移植性バグは Windows の CI が検出しました。`%APPDATA%` を書き換えても Chip Loom の
保存先は移動しません。Windows のプラットフォーム位置は Known Folder API から
取得されるためです。これが `CHIPLOOM_CONFIG_DIR`／`CHIPLOOM_DATA_DIR`／
`CHIPLOOM_CACHE_DIR` を用意した理由であり、統合テストが `HOME` ではなくこれらで
隔離を行う理由です。

### 対応Toolchain

**まだありません。** Toolchain 管理は Phase 2（`v0.3.0-pre.0`）です。ARM GCC・
AVR GCC・RISC-V GCC・Xtensa GCC・LLVM/Clang の自動ダウンロード、SHA-256 検証、展開、
キャッシュ、バージョン固定はそのフェーズで追加します。本リリースはコンパイラを
ダウンロードも、インストールも、呼び出しもしません。

Chip Loom 自体のビルドには Rust stable 1.88 以降、Extension には Node.js 20 以降が
必要です。

### 動作確認内容

以下はすべて Ubuntu 24.04（x86-64）、Rust 1.94.1、Node.js 22.22.2 の環境で、
本リリースに添付した **release** ビルドのバイナリに対して実行しました。

**Phase 0 の完了条件**

```console
$ ./target/release/chiploom --version
chiploom 0.1.0-pre.0        # 終了コード 0

$ ./target/release/chiploom --help
（全コマンド・全オプションを表示、終了コード 0）

$ ./target/release/chiploom doctor
  8 passed, 0 warnings, 0 failures, 3 skipped   (under 1 ms)
  Ready.                    # 終了コード 0
```

**Extension と Rust Core の通信成立。** Extension 自身の JSON-RPC クライアントを、
release バイナリに対して動作させました。モックは一切使っていません。

```console
$ CHIPLOOM_BIN=./target/release/chiploom npm test
# tests 16
# pass 16
# fail 0
```

この16件のテストは、ハンドシェイクの完了、公開される capability の内容、
`core/version`・`core/doctor`・`core/config` の呼び出し、未知のメソッドと不正な
パラメータがセッションを落とさずにエラーとして返ること、`core/ready` 通知の到着、
Core のログがクライアントに届くこと、クライアントの破棄で子プロセスが停止することを
検証します。

同じやり取りをシェルから実行した記録（stdout はプロトコルフレームのみ、
stderr は Extension の Output チャネルに表示される内容）は、上記英語版セクションに
そのまま掲載しています。

**テストスイート**

| スイート | 件数 | 結果 |
| --- | --- | --- |
| `chiploom-core` 単体テスト | 81 | 成功 |
| `chiploom-cli` 単体テスト | 32 | 成功 |
| `chiploom-cli` 統合テスト（実バイナリ） | 25 | 成功 |
| Doc テスト | 1 | 成功 |
| Extension プロトコルテスト（実バイナリ） | 16 | 成功 |
| **合計** | **155** | **成功** |

`cargo fmt --all --check` と、`clippy::pedantic` を有効にした
`cargo clippy --workspace --all-targets -- --deny warnings` はいずれも警告ゼロです。

**テストに加えて手動で確認した挙動**

* 終了コード：成功 `0`、未知のサブコマンド `2`、設定ファイル不正または
  `CHIPLOOM_*` の解析失敗 `3`、診断失敗 `7`、transport 未指定の `serve` `8`。
* 設定の優先順位：プロジェクトファイルが言及しない項目でグローバルの値が残ること、
  環境変数が両者を上書きすること、引数が環境変数を上書きすること、
  `--no-global-config` が実行環境の影響を排除すること。
* `config show` の出力が、`--sources` の有無いずれでも有効な TOML として再解析できること。
* 未知のキーが警告になり、`doctor` にも現れ、`--strict` のときだけ失敗すること。
* 相対指定の `paths.data_dir` が、カレントディレクトリではなくプロジェクトルートを
  基準に解決されること。
* `-vvv` を付けた `serve --stdio` で、stdout の全行が JSON として解釈できること。
* 不正なフレームが `-32700` で応答され、セッションが継続すること。
* stdin を閉じるとエラーなしでセッションが終了すること。
* `--log-file` が1行1 JSON オブジェクトを出力すること。
* bash／zsh／fish／PowerShell の補完スクリプトが生成できること。

### 既知の問題

1. **2つの成果物は一度も実行していません。** `x86_64-apple-darwin` と
   `aarch64-unknown-linux-gnu` はクロスコンパイルであり、リリースワークフロー上で
   実行できません。コンパイルとリンクが通ることのみを確認しており、それ以上は
   主張しません。残る3つは CI とリリースワークフローで実行しており、
   Linux x86-64 はさらに手動で検証しています。
2. **本リリースでは Extension を実際の VS Code ウィンドウに読み込んでいません。**
   プロトコル層（バイナリ探索、ハンドシェイク、全メソッド、エラー処理、終了処理）は、
   実バイナリに対する自動テストで検証済みで、上記の通信記録がその内容です。
   ただし Extension Development Host 上での activate と、VS Code が描画する
   ステータスバー・Output チャネルの表示は、本リリースのビルド環境では実行していません。
   これは Phase 10 の検証計画に含まれており、可能であればそれ以前の Prerelease で
   実施します。
3. **`.vsix` は Marketplace に公開していません。** 添付の `.vsix` を
   `code --install-extension chiploom-v0.1.0-pre.0.vsix` でインストールするか、
   ソースから実行してください。
4. **IPC サーバは単一スレッド・同期実装です。** 同時に扱えるリクエストは1件で、
   キャンセル機構もありません。本リリースのメソッドはいずれもミリ秒単位で完了するため
   これで十分です。ストリーミングとキャンセルは Phase 3（Build Engine）および
   Phase 5（Monitor）で追加します。
5. **`doctor --online` は TCP 到達性のみを確認します。** `github.com:443` と
   `crates.io:443` への接続が張れるかを見るだけで、HTTP プロキシ、TLS 検査、認証は
   検証しません。ダウンロードの完全な検証は Phase 2 で追加します。
6. **macOS 版に署名・notarization はありません。** Gatekeeper に隔離されるため、
   展開後に `xattr -d com.apple.quarantine ./chiploom` を実行してください。
7. **ソースアーカイブからのビルドでは `commit` が `unknown` になります。** この値は
   ビルド時の `git` から取得するため、`.git` を含まない tarball では取得できません。
   リリースワークフローは完全な履歴を取得するので、公開バイナリには記録されます。

### インストール方法

英語版セクションのコマンドをそのまま使用できます。要点は次の3点です。

1. 対象プラットフォームのアーカイブと `.sha256` を両方ダウンロードし、
   チェックサムを検証してから展開してください。
2. macOS では展開後に `xattr -d com.apple.quarantine ./chiploom` を実行してください
   （署名なしのため）。
3. Extension は `code --install-extension chiploom-v0.1.0-pre.0.vsix` で
   インストールしてください。

ソースからビルドする場合：

```bash
git clone https://github.com/Xenoah/chip-loom-mcu-studio.git
cd chip-loom-mcu-studio
cargo build --release
./target/release/chiploom doctor

cd extension && npm install && npm run compile && npm test
```
